## 2. 프로젝트 배경 및 문제 정의 (1:30)

**핵심 시각 자료**
- As-Is 업무 흐름도: `메일함/스캔 파일 → 사람이 읽기 → ERP 화면에 손으로 입력 → 엑셀 원장에 다시 입력`
- 각 단계 옆에 빨간 경고 아이콘: 반복 입력, 오타, 이중 입력

**슬라이드 본문**
- **문제 1. 비정형 입력** — 영수증·세금계산서·청구 메일마다 형식이 다름 → 규칙 기반 자동화가 어려움
- **문제 2. 반복·이중 입력** — 같은 값을 ERP와 엑셀에 각각 수작업으로 입력
- **문제 3. API가 없는 레거시 ERP** — 연동 API가 없으면 결국 사람이 화면에 타이핑해야 함
- **기획 의도** — 해석은 생성형 AI(OCR + LLM), 입력은 RPA, 그 사이에 **사람의 검수 단계**를 둔다

**발표자 스크립트**
> 경리나 총무 업무를 보면, 영수증과 청구 메일을 보고 ERP에 한 번, 엑셀 원장에 또 한 번 입력하는 일이 계속 반복됩니다. 기존 자동화가 잘 안 됐던 이유는 두 가지라고 봤습니다. 첫째, 문서 형식이 제각각이라 정규식 같은 규칙으로는 한계가 있다는 점. 둘째, 회사가 쓰는 ERP에 연동 API가 없는 경우가 많다는 점입니다. 그래서 형식 문제는 생성형 AI로, API가 없는 문제는 사람처럼 화면에 입력하는 RPA로 풀기로 했습니다. 다만 AI가 틀릴 수 있기 때문에 둘 사이에 사람이 확인하고 고치는 검수 단계를 일부러 넣었습니다. 이 결정이 이후 설계 전체에 영향을 줬습니다.

**면접관 어필 포인트**
- 기술보다 **업무 문제를 먼저 정의**했다는 점
- 'AI 완전 자동화'가 아니라 **Human-in-the-loop**를 택한 이유(오입력 비용이 큰 회계 데이터)

## 3. 서비스 핵심 가치 및 솔루션 (1:00)

**핵심 시각 자료**
- 3단 카드 (로그인 화면 좌측 브랜드 패널과 같은 디자인)
  - `01 비정형 문서 수집` · `02 OCR + Gemini 해석` · `03 RPA 자동 입력`

**슬라이드 본문**
- **① 수집** — 파일 업로드(PDF·이미지·EML·HTML·TXT, 10MB) + 이메일 본문 붙여넣기
- **② 해석** — Gemini 구조화 출력으로 거래처·사업자번호·일자·합계·부가세·결제수단·품목·적요 추출, 신뢰도(confidence) 함께 반환
- **③ 입력** — 검수한 값을 엑셀 원장에 적재하거나, Playwright 로봇이 ERP 전표 화면에 타이핑하고 전표번호를 받아 옴
- **+ 운영** — 파싱 성공률·RPA 성공률을 관리자 모니터링으로 추적

**발표자 스크립트**
> 서비스는 세 단계입니다. 문서를 넣으면, AI가 회계 전표에 필요한 항목을 뽑아내고, 사용자가 확인한 뒤 버튼 하나로 엑셀 원장에 쌓거나 로봇이 ERP 화면에 직접 입력합니다. 여기에 운영 관점에서 "AI가 얼마나 잘 읽고 있는지, 로봇이 얼마나 성공하고 있는지"를 볼 수 있는 관리자 모니터링을 붙였습니다.

## 4. 전체 시스템 아키텍처 (1:30)

**핵심 시각 자료** (다이어그램)

```
[Browser]
   │ HTTPS (Bearer JWT)
   ▼
[Frontend] React 19 + Vite ── Render Static Site (dataquill.onrender.com)
   │ REST / CORS 허용 도메인 제한
   ▼
[Backend] FastAPI ── Render Web Service, Docker (dataquill-api.onrender.com)
   ├─ routers: auth · documents · admin · erp_demo
   ├─ services: parser(Gemini/규칙) · oauth · stats
   └─ rpa/: extract(OCR) · excel_writer · erp_typer(Playwright + Chromium)
        │                         │                       │
        ▼                         ▼                       ▼
 [TiDB Cloud Serverless]   [Google Gemini API]   [OAuth: Google/Naver/Kakao]
  (MySQL 호환, TLS)
```

**슬라이드 본문**
- **프런트·백엔드 분리 배포** — 정적 자원과 API의 배포 주기·장애 범위를 분리
- **RPA 엔진은 백엔드 컨테이너에 포함** — Docker 이미지에 Tesseract(한국어) + Chromium 설치
- **DB는 관리형 클라우드(TiDB Serverless)** — 무상태 컨테이너 + 외부 DB → 재배포해도 데이터 유지
- **패키지 경계** — `backend.app`(웹 계층)과 `rpa`(자동화 계층)를 분리, `rpa`는 CLI로 단독 실행도 가능

**발표자 스크립트**
> 구조는 크게 세 덩어리입니다. 정적 프런트, FastAPI 백엔드, 그리고 외부 서비스인 TiDB, Gemini, OAuth 제공자입니다. 프런트와 백엔드를 분리한 이유는 배포 주기가 다르기 때문입니다. 화면만 고쳤는데 RPA가 들어 있는 무거운 백엔드 이미지를 다시 빌드할 필요는 없으니까요. RPA 코드는 `rpa`라는 별도 패키지로 뺐습니다. 웹 서버에서 호출할 수도 있고, 명령줄에서 `python -m rpa.erp_typer`로 단독 실행할 수도 있게 해서, 나중에 별도 워커로 떼어 내기 쉽게 했습니다. 컨테이너는 상태를 갖지 않게 하고 데이터는 TiDB에 두었기 때문에, 재배포하거나 인스턴스가 바뀌어도 데이터가 유지됩니다.

**면접관 어필 포인트**
- 분리 배포의 근거를 **배포 주기와 장애 범위**로 설명
- 지금은 RPA가 API 프로세스 안에서 동기로 실행된다는 한계를 스스로 알고 있음 → 15번 슬라이드의 '작업 큐 분리'로 연결

## 5. 기술 스택 선정 이유 (1:30)

**핵심 시각 자료** (표)

| 영역 | 선택 | 고려한 대안 | 선택 이유 |
| --- | --- | --- | --- |
| API | FastAPI | Flask, Django | Pydantic 스키마로 요청 검증과 응답 모델을 한 번에 정의, OpenAPI `/docs` 자동 생성 |
| LLM | Gemini (구조화 출력) | 프롬프트로 JSON 요청 후 파싱 | `response_schema`에 Pydantic 모델을 넘겨 **스키마를 강제**, 이미지·PDF를 그대로 넣는 멀티모달 |
| RPA | Playwright | Selenium | 요소가 준비될 때까지 자동 대기, `--with-deps`로 Docker 설치가 단순, 헤드리스 기본 |
| OCR | Tesseract + Gemini Vision | 상용 OCR API | 텍스트 레이어가 있으면 pypdf, 없으면 Tesseract, 그것도 없으면 Gemini 멀티모달 순서로 대체 |
| DB | TiDB Cloud Serverless | SQLite, 자체 MySQL | MySQL 호환이라 SQLAlchemy + PyMySQL 그대로 사용, 무료 관리형, 컨테이너 무상태화 |
| ORM | SQLAlchemy 2.0 | Raw SQL | `DATABASE_URL`만 바꾸면 SQLite(테스트) ↔ TiDB(운영) 전환 |
| 프런트 | React 19 + Vite 8 + Tailwind v4 | CRA, styled-components | 빠른 빌드, 유틸리티 클래스 기반 디자인 토큰(`@theme`) |
| 차트 | Recharts | Plotly, Chart.js | React 컴포넌트 방식, 게이지(RadialBar)·누적 막대·도넛을 같은 API로 구성 |

**슬라이드 본문**
- 기준 3가지: **① 1인이 유지보수 가능한가 ② 로컬과 운영이 같은 코드로 도는가 ③ 실패해도 대체 경로가 있는가**

**발표자 스크립트**
> 기술은 세 가지 기준으로 골랐습니다. 혼자 유지보수할 수 있는지, 로컬과 운영이 같은 코드로 도는지, 실패했을 때 대체 경로가 있는지입니다. 대표적인 예가 LLM 부분입니다. 처음에는 프롬프트로 "JSON으로 답해 줘"라고 요청하고 결과를 파싱하는 방식도 생각했는데, 그러면 필드가 빠지거나 형식이 깨지는 경우를 일일이 처리해야 합니다. 그래서 Gemini의 구조화 출력에 Pydantic 모델을 그대로 스키마로 넘겼습니다. 서버의 응답 검증 모델과 LLM의 출력 스키마가 같은 클래스라서 한쪽만 고치면 됩니다. 또 API 키가 없거나 장애가 나도 서비스가 멈추지 않도록 규칙 기반 파서를 대체 경로로 두었습니다. DB는 SQLAlchemy를 써서 테스트는 SQLite, 운영은 TiDB로 URL만 바꿔 돌립니다.

**면접관 어필 포인트**
- **같은 Pydantic 모델을 API 검증과 LLM 출력 스키마에 공유**한 설계
- 대체 경로(fallback)를 여러 겹으로 둔 설계 철학

## 6. 핵심 기술 ① 문서 수집·RPA 자동화 파이프라인 (2:00)

**핵심 시각 자료**
- 단계별 흐름도와 각 단계 담당 모듈

```
업로드 ─▶ extract.py ───────────▶ parser.py ───────▶ 검수(PATCH) ─▶ RPA
          ├ PDF: pypdf 텍스트       ├ Gemini 구조화 출력           ├ excel_writer: pandas+openpyxl
          ├ 텍스트 20자 미만 → Vision├ 실패 시 재시도(백오프)       │  문서ID 기준 upsert
          ├ 이미지: Tesseract(kor+eng)└ 키 없음 → 규칙 파서          └ erp_typer: Playwright
          ├ EML: 헤더+본문(plain/html)                                  셀렉터 맵 → 타이핑 → 저장
          └ HTML: BeautifulSoup 정리                                    → 결과 검증 → 전표번호
```

- 캡처: 데모 ERP 화면(`/erp-demo`)에 로봇이 값을 입력한 뒤 `저장 완료: JV-20261117-0001`이 뜬 화면

**슬라이드 본문**
- **추출 전략** — 텍스트 레이어 우선 → OCR → LLM 멀티모달 순으로 단계적 대체 (`MIN_TEXT_LENGTH = 20`)
- **엑셀 적재** — 같은 문서를 다시 적재하면 **문서 ID 기준으로 교체** → 중복 행 방지, 열 너비 자동 조정
- **ERP 타이핑** — `FIELD_SELECTORS` 맵으로 화면 구조와 코드 분리 → 실제 ERP로 바꿀 때 셀렉터만 교체
- **성공 판정** — 클릭만 하고 끝내지 않고, ERP 응답의 `data-status="ok"`와 전표번호를 확인해야 성공 처리
- **실패 메시지 정리** — Chromium 미설치 같은 환경 오류는 사람이 읽을 수 있는 안내 문구로 변환해 작업 이력에 남김

**발표자 스크립트**
> 파이프라인의 핵심은 "가장 싸고 정확한 방법부터 시도하고, 안 되면 다음 방법으로 넘어간다"입니다. PDF에 텍스트 레이어가 있으면 그냥 읽습니다. 스캔본이라 글자가 20자도 안 나오면 OCR로, OCR 엔진이 없으면 파일 자체를 Gemini에 넘깁니다.
> RPA 쪽에서 신경 쓴 건 두 가지입니다. 첫째, 엑셀 적재를 여러 번 눌러도 행이 중복되지 않도록 문서 ID 기준으로 교체하게 했습니다. 둘째, ERP 입력은 버튼을 눌렀다고 성공이 아니라, ERP가 돌려준 결과 요소의 상태값과 전표번호를 확인한 뒤에야 성공으로 기록합니다. 실제로 운영 환경에서 Playwright가 데모 ERP에 입력하고 전표번호를 받아 오는 것까지 확인했습니다. 화면의 셀렉터는 코드와 분리해 두었기 때문에, 실제 회사 ERP에 붙일 때는 셀렉터 맵만 바꾸면 됩니다.

**면접관 어필 포인트**
- RPA의 고질적인 문제인 **'눌렀는데 실제로는 저장 안 됨'**을 결과 검증으로 막은 점
- 재실행해도 결과가 같은(**멱등**) 엑셀 적재

## 7. 핵심 기술 ② AI 정형화 로직 및 지표 시각화 (1:30)

**핵심 시각 자료**
- 좌: 원문 영수증 텍스트 → 우: 추출 JSON (운영 점검 실제 결과)

```json
{"document_type":"receipt","vendor":"스타벅스 강남R점","business_number":"123-45-67890",
 "date":"2026-11-17","total_amount":9000,"vat":818,"payment_method":"신용카드",
 "items":[{"name":"아메리카노","quantity":2,"unit_price":4500,"amount":9000}],"confidence":0.98}
```

- 하단: 관리자 모니터링 캡처 (성공률 게이지 2개 + 일별 누적 막대)

**슬라이드 본문**
- **스키마** — `ParsedDocument`(Pydantic): 금액은 정수(원), 날짜는 `YYYY-MM-DD`, 없는 값은 null
- **프롬프트 규칙** — "문서에 없는 값은 추측하지 말고 null" + `temperature=0`
- **규칙 파서(대체 경로)** — 날짜·사업자번호·합계·부가세·품목 줄 정규식, 찾은 항목 수로 신뢰도 산출
  - `confidence = 0.2 + 0.15 × (찾은 핵심 필드 수) + 0.1(품목 있음)`
- **운영 지표**
  - AI 파싱 성공률 = `parsed / (parsed + failed)`
  - RPA 성공률 = `success / (success + failed)`
  - 최근 14일 일별 추이(KST 기준), 소스·파서·가입 경로 분포, 평균 신뢰도, 최근 실패 5건

**발표자 스크립트**
> 회계 데이터에서 가장 위험한 건 AI가 그럴듯하게 지어낸 값입니다. 그래서 프롬프트에 "없는 값은 추측하지 말고 null"을 명시하고 temperature는 0으로 고정했습니다. 화면에 보이는 건 운영 환경에서 실제로 뽑힌 결과인데, 품목 단가까지 계산해서 나눠 줍니다.
> 신뢰도 값은 검수 화면에 보여 줘서, 사용자가 어떤 문서를 더 꼼꼼히 봐야 하는지 판단하게 했습니다. 운영 측면에서는 성공률을 정의하는 게 중요했는데요, 아직 처리 중인 문서는 분모에서 빼고 '성공 대 실패'만으로 계산했습니다. 날짜는 서버가 UTC로 저장하기 때문에 통계를 낼 때 한국 시간으로 바꿔서 날짜를 묶었습니다.

**면접관 어필 포인트**
- **지표를 어떻게 정의했는지**(분모에서 대기 상태 제외, 시간대 처리)를 말할 수 있음
- LLM 환각(hallucination)을 프롬프트, 스키마, 사람 검수 3단계로 통제

## 8. 주요 기능 시연 ① 사용자 인증 및 보안 (1:30)

**핵심 시각 자료**
- 로그인 화면 캡처 (좌측 브랜드 패널 / 우측 폼, 비밀번호 규칙 칩이 일부 초록색으로 켜진 상태)
- OAuth 시퀀스 다이어그램

```
브라우저 ─▶ /api/auth/oauth/{provider}/login ── state 난수 생성 → HttpOnly 쿠키 저장 → 제공자로 이동
제공자   ─▶ /callback?code&state ── 쿠키 state와 비교(compare_digest) → 토큰 교환 → 프로필 조회
          ─▶ 계정 연결/생성 → 프런트 /oauth/callback#token=JWT  (URL 해시 → 서버 로그에 남지 않음)
```

**슬라이드 본문**
- **비밀번호 규칙** — 영문 대·소문자 + 숫자 + 특수문자, 8자 이상 / 프런트 실시간 체크 + **서버 재검증**
- **저장** — PBKDF2-SHA256 26만 회 반복 + 솔트, 비교는 `hmac.compare_digest`(타이밍 공격 방지)
- **OAuth 3종** — Google·Naver·Kakao 인가 코드 방식, state 쿠키로 CSRF 방지
- **계정 탈취 방지** — 같은 이메일이 다른 방식으로 가입돼 있으면 자동 연결하지 않고 거부, Google은 `email_verified`, Kakao는 `is_email_verified` 확인
- **테스트 계정 원클릭 로그인** — 일반/관리자 버튼 → 값 자동 입력 후 로그인 (면접관이 가입 없이 바로 체험)

**발표자 스크립트**
> 로그인은 화면은 단순하지만 보안 결정이 가장 많이 들어간 부분입니다. 비밀번호 규칙은 프런트에서 실시간으로 보여 주지만, 프런트 검사는 우회할 수 있으니 서버에서 같은 규칙으로 다시 검사합니다.
> 소셜 로그인에서 제가 특히 신경 쓴 건 계정 탈취입니다. 예를 들어 누군가 제 이메일로 카카오 계정을 만들었을 때, 이메일이 같다고 기존 계정에 자동으로 연결해 버리면 그 사람이 제 계정에 들어올 수 있습니다. 그래서 이메일이 겹치면 연결하지 않고 막았고, 제공자가 이메일 인증 여부를 주는 경우에는 인증된 이메일만 믿습니다. 로그인이 끝나면 토큰을 쿼리 문자열이 아니라 URL 해시로 넘겨서 서버 접근 로그에 토큰이 남지 않게 했습니다.
> 마지막으로 테스트 계정 버튼은 오늘 같은 자리를 위해 만들었습니다. 가입 절차 없이 일반 사용자와 관리자 화면을 바로 비교해 보실 수 있습니다.

**면접관 어필 포인트**
- **OAuth 계정 연결 시 탈취 시나리오**를 고려한 점 (보안 면접 단골 질문)
- 토큰 전달 경로까지 고려

## 11. 주요 기능 시연 ④ 관리자(Admin) 백오피스 (1:00)

**핵심 시각 자료**
- 회원 관리 캡처 (검색창, 권한 필터, 권한 토글, 본인 행의 비활성 토글)
- 접근 제어 3중 구조 도식

```
① 메뉴 노출   : 관리자만 '회원 관리'·'모니터링' 메뉴 표시
② 라우트 가드 : <RequireAuth admin> → 일반 사용자는 대시보드로 이동
③ API 의존성  : Depends(require_admin) → 토큰 없으면 401, 권한 없으면 403   ← 실제 보안 경계
```

**슬라이드 본문**
- 회원 목록 — 이름/이메일 검색(입력 250ms 디바운스), 권한 필터, 가입 방식, 처리 문서 수, 최근 로그인
- 권한 변경 — 토글 + 확인창 → `PATCH /api/admin/users/{id}/role`
- **안전장치** — 본인 관리자 권한 해제 금지(UI 비활성 + 서버 400) → 관리자가 0명이 되는 상황 방지
- 모바일에서는 표 대신 카드 목록으로 전환

**발표자 스크립트**
> 관리자 기능의 핵심은 접근 제어를 세 겹으로 둔 것입니다. 메뉴를 숨기고, 라우트에서 막고, API에서 다시 막습니다. 그런데 앞의 두 개는 사용자 편의를 위한 것이고, 진짜 보안 경계는 서버의 `require_admin` 의존성 하나라고 생각합니다. 테스트에서도 일반 사용자 토큰으로 관리자 API를 호출하면 403, 토큰 없이 호출하면 401이 나오는지 확인합니다. 또 관리자가 실수로 자기 권한을 지우면 관리자가 아무도 없는 상태가 될 수 있어서, 그건 서버에서 400으로 막았습니다.

## 12. DevOps 및 CI/CD 배포 자동화 (1:30)

**핵심 시각 자료**
- 배포 흐름도

```
git push main
   ├─ GitHub Actions (deploy.yml)
   │    ├ paths-filter: 바뀐 영역 판별
   │    ├ frontend/**                         → npm ci · lint · build
   │    └ backend/** · rpa/** · requirements  → pip install · pytest (22개)
   ├─ Render Static Site  (Root Dir: frontend)       → frontend 변경 시에만 빌드
   └─ Render Web Service  (Docker, Build Filter)     → backend·rpa·requirements 변경 시에만 빌드
```

- 환경 변수 구분 표 (`.env.example` 발췌)

**슬라이드 본문**
- **변경 영역만 검증·배포** — 문서만 고친 커밋은 어느 서비스도 다시 빌드하지 않음
- **환경 변수 단일화** — 루트 `.env` 하나로 관리, Vite는 `envDir: '..'`로 같은 파일을 읽음(`VITE_` 접두사만 노출)
- **비밀 값 관리** — `.env`는 Git 제외, 운영 값은 Render 대시보드에 직접 등록, `.env.example`에 `[LOCAL]` / `[RENDER]` / `[RENDER-FE]` 표기
- **Mock 모드** — `VITE_API_URL`이 비어 있으면 브라우저 안의 목업 API로 동작 → 1단계 프런트 단독 배포(Netlify)
- **이미지** — Python 3.11 slim(bookworm) + Tesseract(한국어) + Chromium, `PORT` 환경 변수로 실행

**발표자 스크립트**
> 배포는 main에 푸시하면 자동으로 됩니다. 다만 매번 다 배포하지 않고, 바뀐 영역만 검증하고 배포합니다. 백엔드 이미지에는 Chromium이 들어 있어서 빌드가 몇 분씩 걸리는데, 화면 문구 하나 고쳤다고 그걸 다시 빌드하는 건 낭비니까요. GitHub Actions에서는 바뀐 쪽의 테스트와 빌드를 돌리고, Render는 Build Filter로 자기 영역이 바뀐 경우에만 배포합니다.
> 환경 변수는 루트의 `.env` 하나로 통일했습니다. 프런트 빌드 도구도 같은 파일을 읽게 해서 설정이 두 군데로 갈라지지 않게 했고, 예시 파일에는 각 값이 어디에 등록돼야 하는지 표시해 뒀습니다. 그리고 1단계에서는 백엔드 없이 프런트만 먼저 배포해야 했기 때문에, API 주소가 없으면 브라우저 안에서 돌아가는 목업 API로 전환되게 만들었습니다.

**면접관 어필 포인트**
- 비용·시간을 고려한 **조건부 배포**
- 단계적 출시(목업 → 실 API)를 위한 설계

## 13. 트러블슈팅 (2:30) ★ 면접 핵심

**핵심 시각 자료**
- 사례별 `증상 → 원인 분석 → 해결 → 재발 방지` 4단 카드 3장
- 사례 ①에는 실제 빌드 로그 발췌 (`E: Package 'ttf-ubuntu-font-family' has no installation candidate`)

### 사례 ① 어제까지 되던 Docker 빌드가 갑자기 실패
- **증상** — Render 빌드 중 `playwright install --with-deps chromium` 단계에서 폰트 패키지 설치 실패
- **원인** — 기본 이미지 `python:3.11-slim`의 바탕 OS가 Debian 13(trixie)으로 바뀜. Playwright 1.52 소스(`nativeDeps.ts`)를 확인해 보니 의존성 목록이 Debian 11/12와 Ubuntu에만 있음 → 목록에 없는 OS라 Ubuntu 패키지명으로 설치를 시도하다 실패
- **해결** — `python:3.11-slim-bookworm`(Debian 12)으로 고정, Debian 12에서는 `fonts-unifont` 등 실제 존재하는 패키지를 쓰는 것을 확인
- **교훈** — 움직이는 태그(`slim`)는 재현성을 깬다 → 기본 이미지 OS 버전 고정

### 사례 ② 키를 넣지 않았는데 AI와 OAuth가 '설정됨'으로 동작
- **증상** — 로컬 헬스 체크가 `parser: gemini`로 응답, OAuth 제공자도 모두 활성으로 표시
- **원인** — `.env`에서 `GEMINI_API_KEY=      # 주석`처럼 **빈 값 뒤에 주석**을 쓰면 python-dotenv가 주석 문자열을 값으로 읽음
- **해결** — 모든 주석을 별도 줄로 이동, 규칙 문서화(`AGENTS.md`), 테스트에서는 외부 키를 모두 빈 값으로 고정해 로컬 설정과 무관하게 실행
- **교훈** — 설정은 '들어갔는지'가 아니라 **'어떤 값으로 읽혔는지'**를 확인해야 함 (헬스 체크에 파서 종류를 노출한 덕분에 발견)

### 사례 ③ 운영에서만 실패: TiDB TLS · Gemini 503 · 컨테이너 포트
- **TiDB** — `1105 insecure transport prohibited` → TiDB Serverless는 TLS 필수 → `DB_SSL=true` + certifi CA 번들. 운영 DB는 건드리지 않고 **임시 데이터베이스를 만들어 전체 흐름을 검증한 뒤 삭제**
- **Gemini 503** — 운영 첫 점검에서 "high demand"로 문서가 즉시 실패 → 429/5xx만 골라 2s·5s·10s 백오프 재시도, 400 같은 요청 오류는 바로 실패. 가짜 클라이언트로 재시도 횟수를 검증하는 테스트 3개 추가
- **ERP 타이핑** — 로컬에서 되던 로봇이 운영에서 `localhost:8000` 연결 거부 → Render 컨테이너는 `PORT=10000`으로 실행 → 기본값을 `127.0.0.1:$PORT`로 변경, 오류 메시지에 남은 URL로 원인 확정

**발표자 스크립트**
> 가장 기억에 남는 건 첫 번째 사례입니다. 코드를 하나도 안 바꿨는데 Docker 빌드가 실패했습니다. 로그를 보니 Ubuntu 폰트 패키지를 찾고 있었는데, 저는 Debian 기반 이미지를 쓰고 있었거든요. 추측으로 고치지 않고 Playwright 소스에서 OS별 의존성 목록을 직접 확인했더니, 그 버전은 Debian 12까지만 지원했고, 그 사이에 `slim` 태그가 Debian 13으로 바뀌어 있었습니다. 이미지를 Debian 12로 고정해서 해결했고, 그 뒤로는 기본 이미지 버전을 고정하고 있습니다.
> 두 번째는 설정 파일 문제입니다. 키를 비워 뒀는데 AI 파서가 Gemini로 잡혀 있었습니다. 원인은 빈 값 뒤에 붙인 주석이 값으로 읽힌 것이었습니다. 헬스 체크 응답에 현재 파서 종류를 일부러 노출해 뒀기 때문에 바로 발견할 수 있었습니다.
> 세 번째는 운영에서만 나는 문제들입니다. TiDB는 TLS가 필수였고, Gemini는 사용량이 몰리면 503을 돌려줬고, 컨테이너 안의 로봇은 포트가 달라 자기 자신을 찾지 못했습니다. 공통적으로 저는 운영 DB를 직접 건드리지 않고 임시 DB로 검증했고, 고친 뒤에는 같은 상황을 재현하는 테스트를 추가했습니다.

**면접관 어필 포인트**
- **추측이 아니라 근거(소스 코드·로그·헬스 체크)로 원인을 확정**하는 습관
- 운영 데이터를 보호하면서 검증하는 태도
- 일시적 오류와 영구적 오류를 구분한 재시도 정책

**질문 대비 (발표에서 시간 남으면 언급)**

## 15. 회고 및 향후 고도화 계획 (1:00)

**핵심 시각 자료**
- 좌: 회고 (Keep / Problem) · 우: 로드맵 타임라인

**슬라이드 본문**

**회고**
- Keep — 대체 경로 설계(텍스트 → OCR → Vision, Gemini → 규칙), 화면과 서버 양쪽 검증, 테스트로 재발 방지
- Problem — 외부 의존성(기본 이미지, LLM 가용성, 플랫폼 포트)이 실패 원인의 대부분 → 처음부터 버전 고정과 재시도가 필요했음

**현재 한계 (솔직하게)**
- RPA가 API 요청 안에서 동기로 실행 → 오래 걸리는 작업에 취약
- 업로드 파일이 컨테이너 디스크에 저장 → 재배포 시 원본 유실 가능 (메타데이터와 결과는 TiDB에 유지)
- 스키마 변경을 `create_all`로 처리 (마이그레이션 도구 없음)
- 파싱 품질을 샘플 단위로만 검증 (정량 평가셋 없음)
- 데모 ERP 대상 검증 (실제 ERP 연동 전)

**고도화 계획**
1. RPA 작업 큐 분리 (워커 프로세스 + 진행 상태 조회) → `rpa` 패키지가 이미 분리돼 있어 이전 비용이 낮음
2. 원본 문서를 S3 같은 오브젝트 스토리지로 이전
3. Alembic 마이그레이션 도입
4. 문서 유형별 정답셋을 만들어 필드 단위 정확도 측정 → 프롬프트·모델 비교
5. 실제 ERP 커넥터(API 우선, 없으면 RPA) 및 조직(테넌트) 단위 권한

**발표자 스크립트**
> 돌아보면 제 코드 자체보다 외부 요인에서 더 많이 실패했습니다. 이미지 태그, LLM 서버 상태, 플랫폼 포트 같은 것들이요. 그래서 다음 프로젝트에서는 처음부터 버전을 고정하고 재시도 정책을 먼저 설계할 생각입니다.
> 현재 한계도 분명히 알고 있습니다. 가장 큰 건 RPA가 API 요청 안에서 동기로 돈다는 점이라, 첫 번째 과제로 작업 큐 분리를 잡았습니다. RPA 코드를 처음부터 별도 패키지로 분리해 둔 덕분에 이전 비용은 크지 않을 거라고 봅니다. 그리고 지금은 정확도를 샘플로만 확인했기 때문에, 정답셋을 만들어 필드 단위로 측정하는 것도 다음 단계에 넣었습니다.

**면접관 어필 포인트**
- 한계를 먼저 말하고 **구체적인 개선 순서**를 제시
